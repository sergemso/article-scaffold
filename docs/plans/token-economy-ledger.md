### A.1 Ledger core and key function — [x]
Class: implement · Effort: high · Needs: 0.1 · Check: `.venv/bin/python -m pytest tests/test_ledger.py tests/test_no_network_in_claim_code.py -q`

Do: Create `{{cookiecutter.repo_name}}/scripts/article/ledger.py`.
- `key(kind, inputs, version, tier, tools)` hashes a canonical serialization (sorted names, length-prefixed values, a key-schema version) of file content with newlines normalized, never mtimes. A kind may declare a path as an input where the result depends on it. `tools` are declared statically (a string in the kind or check declaration), never obtained by running a tool.
- `get(root, kind, key)` and `put(root, kind, key, inputs, result)` store one file per key at `docs/ledger/<kind>/<key[:2]>/<key>.json`, written atomically (temp file plus rename). An entry holds the input name to hash map and the result, with no timestamp, so equal results are byte-identical and `put` of an equal result is a no-op. `put` of a different result for an existing key is refused and reported as a conflict. `error` and unavailable outcomes are never stored.
- Provenance (when, tier, procedure version, environment fingerprint) goes in `docs/ledger/<kind>/<key[:2]>/<key>.prov.json`, which may differ between worktrees and is excluded from conflict handling (`.gitattributes` `merge=ours`).
- A kind is registered with its declared input names in one table.
- CLI: `ledger get`, `ledger verify` (recompute keys from the stored input hashes and report mismatches), `ledger explain <kind> <key>` (which input hash differs from the nearest stored entry), `ledger evict <kind> <key> --reason ...` (the only delete; it writes a line to `docs/ledger/evictions.jsonl`), `ledger gc` (report entries whose inputs no longer exist; `--apply` removes them and logs them), `ledger stats` (hits, misses and conflicts counted per run, no content). There is no public `put`: entries are written only by `claims record` and `check record`. `ARTICLE_LEDGER=off` or `--no-ledger` bypasses lookups.
- Add `docs/ledger/` to the template, a `.gitattributes`, and the companion `exclude` default.
Done-when: `tests/test_ledger.py` exists and passes, with a test per registered kind that changes each declared input in turn and asserts the key changes; an unchanged input hits; a CRLF-only change hits; a different result for an existing key is refused; two concurrent `put` calls of the same entry leave one valid file; `error` is refused; eviction is logged; a test that the companion default excludes `docs/ledger/`.
Resolved: `scripts/article/ledger.py`, the `ledger` CLI group, `schemas/ledger-result.schema.json`, `docs/ledger/README.md`, `.gitattributes` and `tests/test_ledger.py` are in. Interpretations worth knowing: (1) the entry schema from 0.1 gained `version`, `tier` and `tools` so `verify` can recompute a key from the entry alone; `get` also recomputes, so a hand-edited entry is refused, not served. (2) Provenance files are named `<key>.<hash of content>.prov.json`, so two writers never collide and no `merge=ours` driver is needed; `.gitattributes` only marks the directory generated. (3) `explain` takes the same inputs as `get` (`--input name=PATH`, `--text name=VALUE`, `--version`, `--tier`, `--tool`), because a bare key cannot say what changed. (4) Registered kinds are `claim-verdict` (inputs `claim`, `excerpt`) and `check-outcome` (open inputs, names are repo-relative paths, so a rename is a miss). (5) `gc` only compares path-input kinds with disk; label-input kinds are never touched. (6) Counters live in `.theses/ledger-stats.json` (untracked). (7) `put` is an API only; the CLI has no verb that writes an entry, asserted by a test. (8) `docs/ledger/**` was already covered by the `docs/**` exclude; the default now names it and `paper/sources/**` explicitly. An existing repo's `companion.yaml` is the author's file and is not changed by `upgrade`, so E.1 must warn about `paper/sources/**` rather than edit it.
